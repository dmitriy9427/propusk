# 09. Режим судо и роли

## Режим судо: «Подтвердите, что это вы»

Вы отошли от ноутбука, не заблокировав экран. Сессия открыта. Коллега-шутник (или вор)
может зайти в настройки, выключить двухфакторную защиту и сменить пароль — и аккаунт
потерян. Чтобы этого не случилось, опасные действия требуют **свежего** подтверждения
личности: не старше 5 минут.

Название — от команды `sudo` в Linux: она тоже просит пароль ещё раз перед действием от имени
администратора.

### На сервере — [server/core.ts](../server/core.ts)

```ts
export function requireRecentAuth(c) {
  if (deps.now() - c.var.session.stepUpAt > 5 * 60 * 1000) {
    throw forbidden('reauth-required', 'Подтвердите, что это вы')
  }
}
```

`stepUpAt` — когда сессия последний раз подтверждала личность. Его ставит:
- **вход** — только что ввёл пароль;
- **`POST /me/step-up`** — пароль, код 2FA или ключ доступа.

Обновление токенов `stepUpAt` **не** продлевает: иначе любая открытая вкладка держала бы
«судо» вечно.

Где требуется:

| Действие | Почему опасно |
| --- | --- |
| сменить пароль | захват аккаунта |
| включить/выключить 2FA, новые коды восстановления | снять защиту или подменить её |
| добавить/удалить ключ доступа | добавить «свою» дверь в аккаунт |
| сменить роль, заблокировать пользователя (админ) | права других людей |

### На клиенте — окно открывается само

Подробно — в [главе 04](04-client.md#подтверждение-личности--окно-которое-открывается-само).
Коротко: `api()` получает 403 `reauth-required`, показывает окно, ждёт подтверждения и
повторяет запрос. Кнопка «Выключить 2FA» про судо ничего не знает.

## Роли и права (RBAC)

RBAC (Role-Based Access Control) — права по ролям. В «Пропуске» две роли: `user` и `admin`.

### Главное правило: проверять на сервере

```ts
// server/routes/admin.ts
app.use(requireAuth, requireRole('admin'))
```

```ts
export const requireRole = (role) => async (c, next) => {
  if (c.var.user.role !== role) throw forbidden()     // роль — из БАЗЫ, не из токена
  await next()
}
```

Раздел «Пользователи» на клиенте скрыт от обычного пользователя, а `requireAdmin` в роутере
не пустит на `/admin`. Но это **удобство, а не защита**: запрос
`fetch('/api/admin/users')` можно отправить из консоли. Защищает только сервер.

Роль берётся **из базы**, а не из JWT. Роль могли поменять минуту назад, а токен живёт ещё
9 минут со старой ролью.

### Изменение прав завершает сессии

```ts
if (body.role && body.role !== target.role) {
  target.role = body.role
  revokeAllSessions(deps, target.id, 'Изменена роль')   // в старых токенах — старая роль
}
if (body.blocked) revokeAllSessions(deps, target.id, 'Заблокирован')
```

Заблокировали — пользователь вылетает **на следующем запросе**: `requireAuth` проверяет и
сессию, и флаг `blocked`.

### Защита от самого себя

```ts
if (target.id === c.var.user.id) throw new ApiError(400, 'self', 'Нельзя менять права или блокировать самого себя')
```

Иначе единственный администратор одним кликом лишит прав сам себя, и некому будет их вернуть.

## Попробуйте сами

1. Войдите как Олег, подождите 5 минут и нажмите «Новые коды восстановления». Что произойдёт?
2. Как Олег заблокируйте Анну, в другом браузере войдя как Анна. Что увидит Анна?
3. Анна (обычный пользователь) открывает консоль и делает `fetch('/api/admin/users')` со своим
   токеном. Что вернёт сервер?

<details>
<summary>Ответы</summary>

1. Откроется окно «Подтвердите, что это вы». После кода из демо-панели появятся новые коды.
2. На следующем запросе её выкинет на вход с пояснением «Сессия завершена на другом устройстве», а войти снова не даст:
   «Учётная запись заблокирована администратором».
3. `403 { code: 'forbidden', message: 'Недостаточно прав' }`.
</details>
