# Уроки: найденные баги

Настоящие ошибки, пойманные при разработке «Пропуска», — с причинами и выводами.

## 1. Сессия терялась после перезагрузки

**Симптом:** вошли, нажали F5 — снова форма входа. При этом ручной запрос `refresh` из
консоли работал.

**Причина:** `createBrowserRouter` вызывался **при импорте** модуля маршрутов. Роутер сразу
запускает первую навигацию, а с ней middleware `requireUser` и запрос `refresh`. Импорты
выполняются раньше кода `main.tsx`, поэтому запрос уходил, **пока демо-сервер (MSW) ещё не
запустился**, — в настоящую сеть, где Vite ответил 404.

**Исправление:** роутер создаётся функцией `createAppRouter()` после `await startMockServer()`.
**Вывод:** у `createBrowserRouter` есть побочный эффект — первая навигация. Порядок инициализации
важен везде, где есть «сервер в браузере», service worker или загрузка конфигурации.

## 2. Выход не завершал сессию, если сразу уйти со страницы

**Симптом:** e2e-тест нажимал «Выйти» и тут же открывал `/login` — и попадал обратно в кабинет.

**Причина:** переход на другую страницу обрывал запрос `POST /auth/logout`. Сессия на
сервере оставалась живой, и следующая загрузка восстанавливала её по cookie.

**Исправление:** `fetch(…, { keepalive: true })` — браузер доводит такой запрос до сервера,
даже если страницу закрыли. **Вывод:** запросы «на выходе» (выход, аналитика, сохранение
черновика) — с `keepalive` или `navigator.sendBeacon`.

## 3. Браузер не даёт ставить cookie из JavaScript

**Проблема:** серверу Hono, запущенному в браузере через MSW, нужно ставить refresh-cookie.
Но `Set-Cookie` и `Cookie` — **запрещённые** заголовки: браузер молча выбрасывает их из
запросов и ответов, созданных скриптом.

**Решение:** мост ([глава 10](10-server.md)): MSW хранит cookie сам, а сервер читает и пишет их
через `readCookie` / `writeCookie`, которые в Node работают с настоящими заголовками.
**Вывод:** запреты браузера на заголовки — не баг, а защита от XSS. В демо её приходится
обходить честно и рассказывать об этом.

## 4. Правило «пароль не содержит почту» запрещало почти любой пароль

**Симптом:** для почты `a@mail.test` любой пароль с буквой «a» отклонялся.
**Причина:** проверка «пароль содержит имя ящика» для имени из одной буквы.
**Исправление:** проверять, только если имя ящика длиннее 3 символов. Тест в [schemas.test.ts](../shared/schemas.test.ts).

## 5. Ожидания e2e-теста после входа по ключу

Тест ждал после входа по ключу страницу «Профиль», а попал в «Безопасность». Это была
**правильная** работа приложения: выходили со страницы «Безопасность», и `next` вернул туда.
**Вывод:** если тест падает, сначала спросите, кто прав — тест или код.

## 6. TypeScript 7 и буферы Web Crypto

`crypto.subtle.deriveBits` не принимал `Uint8Array` из `Uint8Array.from(...)`: тип стал
`Uint8Array<ArrayBufferLike>` (может быть и `SharedArrayBuffer`), а Web Crypto ждёт обычный
`ArrayBuffer`. **Исправление:** создавать массив через `new Uint8Array(length)` и явно
указывать `Uint8Array<ArrayBuffer>`.

## 7. Одноразовые ссылки и двойной запуск эффектов

В режиме разработки `StrictMode` запускает эффекты дважды. Страница «подтвердить почту»
отправила бы токен два раза, и второй ответ «Ссылка недействительна» затёр бы первый успех.
**Решение заранее:** хук `useOnce` с `useRef` ([глава 08](08-email-links.md#одноразовая-ссылка-и-strictmode)).

## 8. Сессия «воскресала» после выхода

**Симптом:** e2e-тест иногда падал: нажали «Выйти», сразу открыли `/login` — и снова в кабинете.

**Причина:** демо-сервер сохранял свою «базу» в localStorage с задержкой 100 мс (чтобы не
писать на каждое изменение). Выход отзывал сессию в памяти, страница тут же перезагружалась,
и запись в localStorage не успевала случиться. Новая страница читала старую базу с живой сессией.

**Исправление:** переходник сохраняет базу **до** того, как отдать ответ странице, плюс
страховка на `pagehide`. **Вывод:** «отложенное сохранение» опасно для данных безопасности —
отзыв доступа должен быть записан до того, как вы сообщили «готово». Настоящая база данных
подтверждает запись транзакцией по той же причине.

## 9. «Выйти» отвечал 500 — только в демо

**Симптом:** после урока 8 тест всё равно падал. Журнал сети показал: `POST /api/auth/logout → 500`.

**Причина:** после урока 2 у запроса выхода появился `keepalive: true`. Переходник MSW
пересоздавал запрос как `new Request(url, request)` — это копирует **все** свойства, в том
числе `keepalive`, а тело становится потоком. Браузер запрещает keepalive-запросам тело-поток,
конструктор бросал ошибку, MSW отвечал 500. Сессия не отзывалась.

**Исправление:** собирать запрос из частей: метод, заголовки и тело, прочитанное заранее
(`await request.arrayBuffer()`). **Вывод:** исправление одного бага (урок 2) создало другой в
соседнем слое. Именно поэтому e2e-тесты прогоняют после каждого изменения, а не «когда-нибудь».
Если 500 приходит от «сервера», который работает в браузере, — смотрите консоль страницы.
